### 0.2 三个决定全局的架构事实

这三点不是细节，它们直接决定了方案怎么设计：

**事实 1：并发是真的，但共享状态是裸的。**
Hyper 为每条消息开线程跑独立事件循环 —— 好事是 100 人不会互相阻塞；坏事是 `user_lists`、`_voice_on`、`cmc.groups` 这些模块级字典被 100 个线程同时读写，**没有任何锁**。`main.py:177-182` 的 `save_voice_prefs` 是"读全量→改→写全量"，两人同时写必然丢一个人的改动；写到一半被另一线程读到还会得到**截断的 JSON**，`load_voice_prefs` 的 `except` 会静默返回 `{}`，表现是"我的音色设置自己变回默认了"。**需求 ④ 的并发设计本质上就是治这个病。**

**事实 2：CPU 活必须出进程边界或进受限池。**
Python 有 GIL。本地 Whisper 推理和 ffmpeg 音效都是 CPU 密集，100 人同时发语音时，串行锁会让第 100 个人等几分钟。既然你选了云端 ASR，这条已经被绕开；剩下的 ffmpeg 音效要放进**固定大小线程池**，不能每条消息随意起。

**事实 3：真正的瓶颈不是 AI，是给 QQ 发消息。**
流式回复会把一段话拆成多条发送（`MAX_MESSAGE_LENGTH = 3`，`AIKernal.py:16`）。100 人并发、每人回复 10 个分片，就是 **17 条/秒**的发送量。QQ 有洪水控制，这个速率会被限流甚至风控。**所以"100 并发"的设计重点在于发送节流与分片合并，而不是在于模型。** 这一条是我在本次审查中新发现的，会直接影响需求 ① 的"每句话都引用"实现方式（见 §1.3）。

### 0.3 ASR 修复记录（2026-10-04 已执行并实测通过）

**重要更正**：本方案初稿把"本地 ASR 已实现"当作已知前提，**这个前提是错的** —— `Tools/asr.py` 代码在，但**从未跑通过**。实测发现两个独立缺陷，均已修复并验证：

| # | 缺陷 | 根因 | 修复 |
|---|---|---|---|
| 1 | `RuntimeError: Cannot load the vocabulary from the model directory` | `models/faster-whisper-base/` 只有 `model.bin`/`config.json`/`tokenizer.json`，**缺 CTranslate2 必需的 `vocabulary.txt`** | 从 HF 镜像补回官方 `vocabulary.txt`（459,861 字节） |
| 2 | `TypeError: open() got an unexpected keyword argument 'metadata_errors'` | faster-whisper 1.2.1 调用 `av.open(..., metadata_errors="ignore")`，而本机 **PyAV 19.0.1 已移除该参数**（其 `open()` 签名确无此项） | 不降级 PyAV；改为**传 numpy 数组**让 faster-whisper 跳过 `decode_audio`，用标准库 `wave` + numpy 自行解码并重采样到 16k |
| 3 | `wave.Error: file does not start with RIFF id` | **edge-tts 保存的文件扩展名是 `.wav`，内容其实是 MP3** —— 判断格式不能看扩展名 | 新增 `_is_riff_wav()` 按**文件头 magic bytes** 判断，非真 wav 交给自带 ffmpeg 转 16k 单声道 |
| 4 | 中文输出为**繁体**且无标点 | Whisper 中文默认行为 | 加 `initial_prompt="以下是普通话的句子，请用简体中文转写，并加上标点符号。"` 作解码偏置 |

|---|---|---|
| wav 端到端 | edge-tts 合成的 7 秒语音 | `这是一段与音时别的测试,如果你能看到这句话,说明本地与音时别已经可以用了。` — 0.9s |

## 1. 需求 ①：私聊"正在输入"气泡 + 全量引用回复

### 1.1 正在输入气泡

NapCat 的接口签名（已核对源码）：

```
POST set_input_status
{ "user_id": "123456789", "event_type": 1 }   # user_id 必须是字符串
```

经 `actions.custom` 调用：`await actions.custom.set_input_status(user_id=str(uid), event_type=1)`

设计为 `Tools/presence.py`：

```python
"""私聊输入状态（正在输入气泡）。
NapCat 实现里 chatType 写死为 C2C，所以只对私聊有效；群聊调用会被忽略。
气泡由 QQ 客户端计时自动消失，发送真实消息也会立刻消掉，因此无需（也没有）显式"停止"接口。
长回复期间靠后台刷新任务维持可见。
"""
import asyncio

REFRESH_SECONDS = 4.0

async def _send(actions, user_id, event_type=1):
    try:
        await actions.custom.set_input_status(user_id=str(user_id), event_type=event_type)
        return True
    except Exception as e:
        # 非好友 / uid 解析失败时 NapCat 抛 "uid is empty"，静默降级即可，不能影响回复
        print(f"[presence] 输入状态发送失败（{user_id}）：{e}")
        return False

async def typing_bubble(actions, event, enabled=True):
    """异步上下文管理器：进入时亮气泡，期间每 REFRESH_SECONDS 刷新一次，退出时停。"""
```

要点：
1. **只在私聊调用**（`getattr(event, "group_id", None) is None`），群聊不调（调了也是无效请求，白白浪费一次往返）。
2. **必须 try/except 静默降级**。NapCat 源码 `:77292-77293` 走 `getUidByUinV2`，非好友会抛 `uid is empty`；这绝不能打断回复流程。
3. **长回复要刷新**。QQ 客户端的气泡大约几秒后自动消失，而一次 AI 流式回复可能 10~20 秒。方案是用 `asyncio.create_task` 起一个每 4 秒重发的刷新协程。因为每条消息本来就跑在独立的 `asyncio.run()` 里，这个 task 的生命周期天然隔离，不会串到别人。
4. 在 `main.py` 私聊分支（`:789`）最靠前的位置开启，覆盖到 AI 回复、语音合成、ASR 整个耗时区间。

### 1.2 全量引用回复

现状：`AIKernal.send_message` 私聊分支不带 `Reply`；而 `main.py` 私聊里有 **约 30 处**直接 `actions.send(user_id=...)`（帮助、音色、语音、预设、高数、模型切换……），全都是裸发。

要做到"不管发送什么消息都以引用方式回复"，**不能逐处去加 `Segments.Reply`** —— 30 处必有遗漏，且以后新增命令还会漏。正确做法是收敛到一个统一出口：

`Tools/reply.py`：

```python
async def reply_send(actions, Manager, Segments, event, message, quote=None):
    """统一的回复出口：私聊/群聊自动判定，并按需附加引用段。

    quote=None  -> 跟随配置（私聊默认开，群聊沿用原有"仅首条引用"行为）
    quote=True  -> 强制引用
    quote=False -> 强制不引用
    """
```

本次改造范围：
- `AI_bot/AIKernal.py:175-193` 的 `send_message`：私聊分支改为带 `Segments.Reply(self.event.message_id)`。
- `main.py` 私聊分支的 30 处 `actions.send(user_id=...)` 全部替换为 `reply_send(...)`。
- 语音发送 `Tools/tts_local.py:207` 的 `speak_and_send` 私聊分支同样支持带引用。

配置开关（写进 `config.json`，便于你随时关掉）：
```jsonc
"Others": {
  "private_reply_quote": true,     // 私聊每条回复都引用原消息
  "private_typing_bubble": true,   // 私聊显示"正在输入"
  "quote_only_first_chunk": true   // 见下方 1.3
}
```

### 1.3 ⚠ 两个必须提前知道的取舍

**取舍 A：流式分片是否每条都引用？**
一次回复被拆成多个分片时，如果每个分片都带引用，QQ 里会看到连续 5~8 个"引用同一条消息"的气泡，观感很吵，而且**每条都带引用段会让单条消息体积变大、发送次数翻倍**，加剧事实 3 的洪水控制问题。

我的建议：`quote_only_first_chunk: true` —— **首片带引用（明确"这是在回你这条"），后续片作为续写不带**。这既满足"以引用方式回复"的语义，又不炸屏。如果你要严格"每条都引用"，把该开关置 `false` 即可，方案已支持。

**取舍 B：分片合并。**
为了同时满足"100 并发不被 QQ 风控"和"不要一条回复刷 8 条消息"，建议在 `AIKernal.handle_message_stream`（`:145-173`）加一个**合并缓冲**：收到分片先攒着，满足「累积 ≥ 60 字」或「距上次发送 ≥ 1.2 秒」才真正发一条。这会**顺带改善单用户体验**（回复更少更完整），并把发送次数压到原来的 1/3 左右。这是需求 ④ 能承载 100 人的前提之一。

## 2. 需求 ②：云端语音转文字

### 2.1 为什么云端是可行且划算的

已确认 **OpenAI 兼容的 `/v1/audio/transcriptions` 是事实标准**：硅基流动（`FunAudioLLM/SenseVoiceSmall`）、Groq（whisper-large-v3）、OpenAI、阿里云 DashScope 兼容模式（qwen3-asr-flash）、自建端点，全都用同一套请求格式：

```
POST {base_url}/audio/transcriptions
Authorization: Bearer <key>
Content-Type: multipart/form-data
  file=<音频>
  model=<模型名>
```

本机已装 `openai 1.109.1`，直接用 `client.audio.transcriptions.create(model=..., file=...)`，**零新依赖**。

**一个容易被忽略的点：云端 ASR 并不能省掉 silk 解码。** QQ 语音是 silk v3 编码，云端接口只吃 wav/mp3/ogg/m4a。所以 `Tools/asr.py` 里现有的 `_decode_silk_to_wav()`（pysilk 优先、ffmpeg 回退）**必须保留**，云端方案只是把最后那一步"wav → 文字"从本地改成了 HTTP。

### 2.3 并发与健壮性（这是需求 ④ 的一部分）

现有 `_RUN_LOCK` 把转写完全串行化，100 人同时发语音会排长队。改造为：

| 项 | 方案 |
|---|---|
| 并发闸门 | `asyncio.Semaphore(asr_concurrency)`（云端默认 12）；本地后端改为固定 `ThreadPoolExecutor(max_workers=2)`（CPU 密集，不能放开） |
| 超时 | 单条 15 秒硬超时，超时降级到下一个 provider，全失败则回 `（语音内容未能识别）` |
| 重试 | 429/5xx 指数退避重试 2 次（0.5s / 1.5s）；4xx 不重试 |
| 单飞去重 | 用音频内容 sha256 做 key 的 `SingleFlight`：同一段语音被并发请求只真正转写一次（转发语音很常见） |
| 结果缓存 | LRU 512 条（key = sha256(audio) + provider），命中直接返回，秒回 |
| 长度/体积护栏 | 解码后 wav 超 60 秒或超 5MB → 拒识并回一句友好提示，不浪费配额 |
| 熔断 | provider 连续失败 5 次 → 熔断 60 秒，期间直接用下一个 provider |

### 2.4 顺带可做的小增强（可选，建议一起）

现在语音转写后**用户看不到转写结果**（`main.py:2120` 只是把内容塞进 `event.message` 供 AI 使用）。建议加一个开关 `asr_echo: true`，识别后先回一行灰色小字「🎧 我听到：xxx」——**这会极大降低"机器人答非所问"时的困惑**，因为用户能立刻发现是识别错了还是理解错了。对调试和体验都是正向的。

## 3. 需求 ③：音色丰富化

### 3.1 现状与它的真实瓶颈

现有 7 个音色（`Tools/tts_local.py:25-35`）。文件里的注释点出了根因：

> 微软较新的 Latest 语音（Xiaohan/Xiaorui/Xiaomo/Xiaochen 及 Yunze 云泽）在该端点不返回音频（No audio was received），故不收录

也就是说：**音色不是"加一行就行"，而是"加了之后不一定能出声"**，而且不同网络/时间点表现还会变。所以方案的第一要务不是堆数量，而是**把"能不能出声"变成可自动检测的事实**。

### 3.2 三段式方案

**第一段：启动自动探活（解决"选了没声音"）**

新增 `Tools/tts_health.py`：启动时对候选音色各合成一句极短的"测试"，成功的记进 `data/voice_health.json`，失败的打标记。`~音色` 列表**只展示探活通过的**，并显示上次检测时间。加新音色后不需要人工试错。

探活本身异步、限流（并发 3），失败不阻塞启动。

**第二段：扩容音色表（7 → ~30）**

按类别组织，全部是 `edge-tts` 端点**已知存在**的 id，最终以探活结果为准：

| 类别 | 音色示例 | 趣味点 |
|---|---|---|
| 经典普通话女声 | 小艺、晓晓、晓萱 + 新增 晓伊、晓悠 | 基础盘 |

命令形态设计（与现有 `~语音` 语法一致，不增加学习成本）：
- `~音色 花栗鼠`、`~音色 东北话`、`~音色 粤语`
- `~音色 随机` —— 每次回复随机换音色（趣味性最强）
- `~音色 情绪` —— **根据回复文本情绪自动选音色**（见下）

**情绪联动（强烈推荐）**：从回复文本里做轻量情绪判定（关键词 + 标点，如 `！`/`？`/笑/哭/颜文字），开心时用晓晓、生气时用云健加大叔音效、安慰时用晓伊放慢。这让"音色丰富"从"有个列表可选"变成"人物是活的"。

### 3.3 角色 × 音色绑定

现有 `prerequisites/current.json` 的多角色预设（`~角色扮演`）可以**绑定默认音色**：切到"春日野悠"就自动换成少年音，切到另一个角色换成御姐音。配置加在预设的元数据里，`voice_sel_for()` 的解析顺序变为：

```
用户显式选择 > 当前角色绑定音色 > 用户偏好 > 全局默认
```

这条把需求 ③ 和需求 ④（用户偏好存储）、现有角色系统三者串了起来。

## 4. 需求 ④：用户识别 + 用户参数 + 100 并发

这是五项里最大的一块，拆成 4 个部分：**存储 → 识别 → 画像应用 → 并发加固**。

### 4.1 存储：换 SQLite（WAL）

**为什么必须换掉 JSON**：`voice_prefs.json`、`consent_asked.json` 都是"整文件读 → 改 → 整文件写"，没有锁。100 人并发下必然出现：① 后写覆盖先写（丢设置）；② 读到写了一半的截断 JSON（`except` 静默返回 `{}`，设置"自己变回默认"）。这是**已经存在的数据损坏风险**，不是假设。

设计：`data/fox.db`，SQLite + WAL：

```sql
PRAGMA journal_mode = WAL;      -- 并发读 + 单写，不互相阻塞
PRAGMA synchronous = NORMAL;    -- 性能与安全的平衡点
PRAGMA busy_timeout = 5000;     -- 写锁等待 5 秒而不是立刻报错
PRAGMA foreign_keys = ON;
```

**连接管理**：Hyper 是"一消息一线程"，所以用 `threading.local()` 给每个线程各持一个连接（SQLite 连接不可跨线程复用）。写操作靠 WAL + `busy_timeout` 串行化，计数类更新一律用**原子 SQL**（`UPDATE users SET msg_count = msg_count + 1`）而不是"读出来加一再写回"。

选型理由：`sqlite3` 是 Python 标准库（**零新依赖**），单文件便于备份，WAL 模式下 100 个并发小读写的实际吞吐远超本场景需求。

### 4.2 数据模型

```sql
-- 用户档案（身份 + 行为统计 + 好感度）
CREATE TABLE users (
  qq          TEXT PRIMARY KEY,
  nickname    TEXT,                 -- 最近一次已知昵称
  card        TEXT,                 -- 群名片
  gender      TEXT, age INTEGER, level INTEGER,   -- 来自 get_stranger_info / get_group_member_info
  first_seen  INTEGER NOT NULL,     -- epoch
  last_seen   INTEGER NOT NULL,
  msg_count   INTEGER DEFAULT 0,
  voice_count INTEGER DEFAULT 0,
  ai_count    INTEGER DEFAULT 0,
  char_count  INTEGER DEFAULT 0,
  active_days INTEGER DEFAULT 0,
  streak_days INTEGER DEFAULT 0,    -- 连续互动天数
  affinity    INTEGER DEFAULT 0,    -- 好感度
  affinity_today INTEGER DEFAULT 0, -- 每日上限用
  affinity_date  TEXT,
  relation    TEXT DEFAULT '陌生',  -- 陌生/眼熟/熟人/挚友
  nickname_pref TEXT,               -- ~叫我 xxx 设置的称呼
  tags        TEXT DEFAULT '[]',    -- JSON 数组
  note        TEXT,                 -- 管理员备注
  revoked     INTEGER DEFAULT 0     -- "忘记我"软删除标记
);

-- 偏好（每用户一份）
CREATE TABLE prefs (
  qq TEXT PRIMARY KEY REFERENCES users(qq) ON DELETE CASCADE,
  voice TEXT, model TEXT, preset TEXT,
  reply_quote INTEGER, typing_bubble INTEGER,
  asr_enabled INTEGER, tts_enabled INTEGER,
  extra TEXT DEFAULT '{}'
);

-- 群级偏好（模型/音色的群默认）
CREATE TABLE group_prefs (
  group_id TEXT PRIMARY KEY, model TEXT, voice TEXT, extra TEXT DEFAULT '{}'
);

-- 互动流水（可裁剪，用于"上次聊到"和统计）
CREATE TABLE interactions (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  qq TEXT NOT NULL, ts INTEGER NOT NULL,
  kind TEXT,                        -- text/voice/image/command
  group_id TEXT, summary TEXT
);
CREATE INDEX idx_inter_qq_ts ON interactions(qq, ts DESC);

-- 迁移来源：voice_prefs.json / consent_asked.json / voice_sel
```

**迁移脚本**：首次启动自动把现有 `voice_prefs.json`（`on`/`seen`/`voice`）与 `consent_asked.json` 导入 `prefs`，原文件重命名留档。**平滑升级，不丢现有设置。**

### 4.3 用户识别（分层）

**第一层 · 身份识别**
- 主键 = QQ 号（私聊 `event.user_id`；群聊 `event.user_id` + `group_id`）。
- 群聊补充 `actions.get_group_member_info(group_id, user_id)` → 群名片、头衔、角色（owner/admin/member）、入群时间、等级。
- 私聊补充 `actions.get_stranger_info(user_id)` → 昵称、性别、年龄、等级。
- **这些都带 `@Logic.Cacher().cache_async`，但缓存无 TTL** —— 100 人场景下昵称改了不会更新。设计加一层本地 TTL 缓存（如 24 小时），既省 API 调用又能刷新。

**第二层 · 画像注入（关键：让机器人"认得"人）**
在 `presets_tool.gen_presets()` 生成 system prompt 时，追加一小段**极简**画像（控制 token 成本，只放 2~3 行）：

```
【当前对话者】小明（QQ 等级 32）｜关系：熟人（好感度 128）｜今天第 5 次找我
【偏好】叫我"明明"｜喜欢用语音｜常用音色 云希
【上次】昨天聊到「想学 Python 爬虫」
```

这一段是"用户识别"真正产生体感的地方 —— 机器人会叫对你的名字、记得你是老熟人、知道你昨天聊过什么。**Token 成本必须控制**，所以只放摘要，不放流水。

**第三层 · 好感度机制**
| 行为 | 好感度 |
|---|---|
| 每次对话 | +1（每日上限 30，防刷） |
| 发语音 | +2 |
| 被夸（"小狐狸真棒"） | +3 |
| 连续互动天数 bonus | +streak_days（上限 +7） |
| 被骂（辱骂词表） | −5 |
| 触发风控/刷屏 | −10 |

关系档位：陌生(0-20) / 眼熟(21-60) / 熟人(61-150) / 挚友(151+)。
**应用**：影响称呼、语气亲密度、是否主动打招呼、是否愿意开语音。让"用户参数"不只是个数据库字段，而是真的改变行为。

**第四层 · 管理员工具**
`~用户 <QQ>` 看档案 / `~用户列表` / `~叫我 <昵称>`（用户自助改称呼）/ `~好感度 @人 +10`（管理员调整）/ `~备注 <QQ> <文字>`。

### 4.4 并发加固（100 人的真正保障）

| # | 风险点 | 现状 | 方案 |
|---|---|---|---|
| 1 | 偏好 JSON 丢写/损坏 | `main.py:177-182` 无锁整文件写 | 迁移到 SQLite，原子 UPDATE |
| 2 | `consent` 丢写 | `main.py:97-104` 同上 | 同上 |

### 4.5 容量测算（100 并发是否真的撑得住）

假设：100 人在线，人均 60 秒发 1 条 → **稳态 ~1.7 条/秒**，突发按 10 条/秒设计。

| 环节 | 单次成本 | 100 并发下的状态 | 结论 |
|---|---|---|---|
| 云端 ASR | 1~3 秒/条 | 语音占比 20% → ~0.3 条/秒 | 轻松，信号量 12 绰绰有余 |
| 本地 Whisper（若降级） | 1~3 秒/条（CPU int8） | 串行锁下 100 条 = 100~300 秒 | **不可接受 → 云端为主、本地仅兜底** |
| LLM（云端流式） | 首字 0.5~2s，整段 5~15s | 100 个在飞请求 | 取决于中转站并发上限；信号量 40 + 排队，p95 等待数秒 |
| TTS（edge-tts） | 1~3 秒/次 | 信号量 16 + 缓存命中后近 0 | 可接受 |
| **QQ 发送** | — | 未合并时 ~17 条/秒 | **瓶颈** → 必须合并分片 + 令牌桶 |
| SQLite 写 | <1ms | ~10 写/秒 | 毫无压力 |
| 内存 | 100 用户 × 6 轮 × ~500 token ≈ 300KB | — | 毫无压力 |
| 线程 | 100 线程 + 各自事件循环 | — | Python 线程栈开销可接受；CPU 活已移出 |

**结论：只要做到 ① ASR 走云端 ② 发送侧合流限速 ③ CPU 活进受限池 ④ 共享状态换 SQLite，单进程承载 100 并发是现实的。** 真正的天花板是 QQ 侧的洪水控制，而不是机器人自身。

### 4.6 隐私（用户档案 = 个人信息，必须处理）

- 数据**仅存本机** `data/fox.db`，不上传。
- 发给第三方 LLM 的只有 **2~3 行摘要**，绝不发完整档案与流水。
- 提供 `~忘记我`：物理删除该用户全部记录（`revoked` 软删 + 定时清理）。
- 保留策略：`interactions` 流水默认保留 90 天，定时任务裁剪。
- 首次私聊的同意询问（现有 `consent_asked`）**保留**，并在文案里补一句"会记录基本资料用于更好地陪你聊天"。

## 5. 需求 ⑤：多模型切换

### 5.1 现状的三个硬伤

1. **全局变量**：`main.py:132` 的 `EnableNetwork` 是模块级全局，`:1107-1135` 直接赋值。**A 用户发 `~Gemini`，B、C、D 所有人一起被切走。** 这是当前最严重的功能缺陷之一。
2. **模型与后端耦合在字符串里**：模式名（`Ds`/`Net`/`GPT-3.5`/`GoogleGemini`/`WebSearch`）既当"用哪个供应商"又当"走哪条代码链路"，加一个新模型要改 `AIKernal` 的 `match` 分支。
3. **Gemini 的模型名在 Context 创建时固化**（`ContextManager.py:22,32`），切模型不会生效，必须重建。

### 5.2 方案：模型注册表 + 三级作用域

**配置结构**（`config.json` 新增，`providers` 与 `registry` 分离 —— 供应商复用，模型可多挂）：

```jsonc
"models": {
  "providers": {
    "relay":    { "type": "openai", "base_url": "https://discovery-api.intern-ai.org.cn/v1",
                  "key_env": "JIANER_API_KEY", "extra_headers": {} },
    "silicon":  { "type": "openai", "base_url": "https://api.siliconflow.cn/v1",
                  "key_env": "SILICONFLOW_API_KEY" },
    "local":    { "type": "openai", "base_url": "http://localhost:1234/v1", "key_env": "" },
    "gemini":   { "type": "gemini", "base_url": "https://generativelanguage.googleapis.com/",
                  "key_env": "GEMINI_API_KEY" }
  },
  "registry": [
    { "id": "ds-chat",   "provider": "relay",   "model": "deepseek-chat",
      "label": "DeepSeek 对话", "tags": ["通用", "快"], "aliases": ["deepseek", "ds"] },
    { "id": "ds-think",  "provider": "relay",   "model": "deepseek-reasoner",
      "label": "DeepSeek 推理", "tags": ["推理", "慢"], "reasoning": true, "aliases": ["推理"] },
    { "id": "sf-qwen",   "provider": "silicon", "model": "Qwen/Qwen2.5-72B-Instruct",
      "label": "通义千问 72B", "tags": ["通用"] },
    { "id": "local-gemma","provider": "local",  "model": "google/gemma-3-4b",
      "label": "本地 Gemma",  "tags": ["离线", "免费"] },
    { "id": "gemini-flash","provider":"gemini", "model": "gemini-2.0-flash-exp",
      "label": "Gemini Flash", "tags": ["多模态", "看图"] }
  ],
  "default": "ds-chat",
  "fallback_chain": ["ds-chat", "sf-qwen", "local-gemma"]
}
```

**三级作用域（就近优先）**：
```
用户偏好（prefs.model）  >  群默认（group_prefs.model）  >  全局默认（models.default）
```

**QQ 命令族**：

| 命令 | 作用 | 权限 |
|---|---|---|
| `~模型` | 列出全部模型：编号 / 名称 / 标签 / 健康状态 / 当前标记 | 所有人 |
| `~模型 3` 或 `~模型 推理` | 切我自己的模型（**立即生效，只影响我**） | 所有人 |
| `~模型 群 <名>` | 设置本群默认 | 管理员 |
| `~模型 全局 <名>` | 设置全局默认 | ROOT |
| `~模型 自动` | 开启智能路由 | 所有人 |
| `~模型 状态` | 各 provider 健康度 / 延迟 / 熔断状态 | 管理员 |
| `~云端` / `~本地` | 保留为 `~模型 ds-chat` / `~模型 local-gemma` 的快捷方式 | 所有人 |

**智能路由 `~模型 自动`**：按任务特征选模型 —— 带图 → 多模态；含代码/数学/"推理"关键词 → 推理模型；超短闲聊 → 快模型；云端全部不可用 → 本地模型。

### 5.3 改造点

| 位置 | 改动 |
|---|---|
| `main.py:132` | 删除全局 `EnableNetwork`，改为**每请求解析** `resolve_model_for(event, registry)` |
| `main.py:1107-1135` | 模式切换命令 → 改为 `~模型` 命令族，写入用户/群偏好而非全局变量 |
| `AI_bot/AIKernal.py:38-102` | `generate_response(..., model_id=...)`；`match EnableNetwork` 改为按 `provider.type` 分派（`openai` / `gemini`），新增模型不再改此处 |
| `Tools/ai_backend.py:40-65` | `resolve()` 改为接收 `model_id`，查注册表返回 `(base_url, model, extra_body, provider_type)`；保留旧签名兼容 |
| `Tools/deepseek.py:89` | 使用 `ai_backend.resolve(model_id)`；客户端加**模块级复用缓存** |
| `AI_bot/ContextManager.py` | `Context` 记住所用 model_id；**切模型时自动重建该用户 Context** 并在群里提示"已切换，上下文已重置" |
| `Tools/web_search.py` | 联网链路的系统提示改为从 config 现取（既有问题） |

**关键设计决定：切换模型时该用户上下文怎么办？**
不同模型共享同一份历史会导致格式不兼容（Gemini 的 `Context` 与 OpenAI 的 messages 结构不同）。方案：**切模型 = 重建该用户的 Context**，并明确告知用户（"已切换到 X，上下文已重置"）。这比"悄悄带着不兼容历史发出去然后报 400"好得多。

### 5.4 健康检查与自动降级

- 启动 + 每 5 分钟：对每个 provider 发一次最小请求探活，结果存内存 + `data/model_health.json`。
- `~模型` 列表里用 ✅/⚠️ 标注，不可用的排在后面并说明原因（无 Key / 超时 / 429）。
- 请求失败时按 `fallback_chain` 自动降级到下一个可用模型，并告知用户"主模型不可用，已临时切到 X"。
- 与 §4.4 的熔断器复用同一实现。

## 7. 风险与验收

### 7.1 主要风险

| 风险 | 影响 | 应对 |
|---|---|---|
| `set_input_status` 在非好友/特殊账号失效 | 气泡不显示 | 已设计静默降级，不影响任何功能；真机上先做一次冒烟验证 |
| 私聊 `Reply` 段某些 QQ 版本渲染异常 | 引用显示为文本 | 提供 `private_reply_quote` 开关一键关闭；保留不带引用的回退路径 |
| 云端 ASR 服务商合规/隐私 | 语音上传第三方 | 音频仅上传用户主动发送的语音；提供 `asr_backend: local` 一键切回全离线；文档明示 |
| 第三方中转站不可信（既有问题） | 对话内容经第三方 | 多 provider 后用户可自选；建议至少配一个本地模型作兜底 |
| 100 并发下 SQLite 写锁竞争 | 偶发 5 秒等待 | WAL + `busy_timeout` + 原子 UPDATE + 写操作尽量合并；压测验证 |
| 模型切换重建上下文惹用户不满 | 体验 | 明确提示 + 保留"临时切换，不重置"选项 |
| 改动面大（`main.py` 2132 行） | 回归风险 | 分阶段提交，每阶段跑语法检查 + Flask test client 冒烟 + 纯函数单测；P0/P1 先行评审 |

### 7.2 验收标准

| 需求 | 验收方式 |
|---|---|
| ① 气泡 | 私聊发消息，对端 QQ 在 AI 回复期间持续显示"正在输入"；回复 20 秒不消失 |
| ① 引用 | 私聊发送 ≥5 类消息（普通提问、`~帮助`、`~语音`、`~音色`、`~模型`），每条回复都带引用 |
| ② ASR | 发送语音，转写结果正确且不回显错字；断网时自动落本地；同一段语音二次发送命中缓存秒回 |
| ③ 音色 | `~音色` 列出 ≥20 个可用音色；方言/粤语/日语/音效预设均能出声；`~音色 随机` 每次不同 |
| ④ 用户参数 | `~用户 <QQ>` 返回完整档案；画像注入后机器人能叫对昵称与称呼；好感度随互动正确变化且每日封顶 |
| ④ 100 并发 | **压测脚本**：模拟 100 个并发会话持续 10 分钟，断言 ① 无 JSON/SQLite 损坏 ② 无交叉串音（TTS 文件不覆盖）③ 无未捕获异常 ④ 发送速率未触发 QQ 风控 ⑤ 记录 p50/p95 延迟 |
| ⑤ 模型切换 | A 用户切模型后 B 用户模型不变；`~模型` 列表标出健康状态；主模型故障时自动降级且有提示 |

**关于并发测试的说明**：本机没有真实 QQ 负载，所以会用**打桩方式**（mock `actions.send` / `get_stranger_info`，保留真实并发路径）压 `Tools/userstore.py`、`Tools/asr.py`、`Tools/tts_local.py` 三个模块的线程安全。真实 QQ 洪水控制的验证只能真机小规模试（比如 10 个真人同时发），压测结果我会明确标注哪些是打桩、哪些是真机。

### 7.3 我建议你先确认的几点

1. **分片是否每条都引用**（§1.3 取舍 A）：推荐"仅首片引用"，你要严格全引用也能做。
2. **是否接受"发送侧合流限速"**（§1.3 取舍 B）：这是 100 并发的前提，代价是流式回复的"逐字蹦"效果会变成"每 1.2 秒蹦一段"。
3. **云端 ASR 服务商**：方案默认硅基流动 + Groq 双 provider 回退。你要用哪家？需要对应环境变量。
4. **是否保留本地 Whisper 作为兜底**：保留更稳（断网可用），代价是 `models/` 里那 145MB 不删。
5. **好感度数值是否要自定义**：默认按 §4.3 的表，你可以直接改。
